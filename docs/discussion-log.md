## 2026-10-01 16:57 — 需求讨论（八）：半小时两段闸，与远程强制终止

恩公把等待策略按简单方向收了，又添了一件硬需求：

- **阈值定案**：命令停在需要回应的地方（比如 sudo 密码提示）
  半小时没动静，客户端通知对话侧，云端在对话里告知他需要互动；
  通知后再半小时没动静，云端把这个任务停掉并挂起。此条取代

- **远程强制终止（新需求）**：强制终止命令一定要有。场景是命令
  卡死或跑个没完（比如 find 在找一个不存在的文件），他想停时
  在对话里下令就行，不必去本地客户端按 Ctrl+C。助手已核实网关
  submit 对 kind 透传存储：控制任务（终止当前命令）可借现成的

  任务，终止走 SIGINT→SIGTERM→SIGKILL 阶梯（DESIGN §3.2.3）。
- **免密 sudo 预先约定**：可以事先约定一批免密 sudo 命令走名单

  要留神：名单内的命令将不再逐次停顿等他确认，因此每条纳入前

## 2026-10-01 16:47 — 需求讨论（七）：等待两段式——先通知，再挂起

恩公给上一轮的无限等待装了闸：

- 命令停在需要他回应的地方，一个小时没有互动（用户不应答），
  客户端先通知对话那侧，让云端在对话里告知他需要互动。
- 通知后还是没回复，这个任务就地挂起：记录停在哪个地方，等他
  下次开启客户端会话时提醒他处理。
- 于是（六）的无限等待有了收尾：等 → 催 → 冻存待办。Ctrl+C 与
  退出客户端两个终止手段不变；挂起是冻结存档，不是超时强杀。

待细化已记入 DESIGN §3.2.4：在等信号怎么过网关；挂起时被等住
的进程杀掉重跑还是冻结续跑；停点字段；下次会话的自检提醒；
通知后再等多久挂起（助手暂记再 1 小时，待恩公确认）。

## 2026-10-01 16:37 — 需求讨论（六）：v1 只做 shell、等待不限时、提示符醒目化

恩公把需求清单余下的问题一次给了说法：

- **命令种类**：第一版只做 shell，解决给云端当手和跑腿的问题；
  更宽的任务概念先不碰。
- **不在机器旁**：命令一直等待，比如停在 sudo 密码提示处就那么
  停着，等他回来，不限时。
- **失败与超时**：记入 JSON 就好。恩公反问助手所说的超时指哪边
  ——VM 等不到回应的超时，还是客户端自定的执行超时。结论（与

  网关既有参数（任务/结果 TTL 2 小时、无结果 15 分钟重投递）与
  可以等很久的配合问题，留设计阶段（task_id 去重须跨重启有效）。
- **提示符醒目化**（恩公新加）：进入 Python 程序后提示符要换成
  醒目的样子，如 `(muse)` 前缀（像 conda 的 `(base)`）或彩色
  背景；退出回到原 shell 即恢复，一眼看得出自己在哪。

需求层至此基本过完，仅剩常驻方式（DESIGN §3.1.6）在现模型下

## 2026-10-01 15:48 — 需求讨论（四）：按系统的入口名与会话文件

恩公把整体模型复述成一段完整的使用过程，并补了三处具体设定：

- **入口按系统命名**：打开 Terminal 运行 `python muse_macos.py`
  （或 `muse_win11.py`、`muse_ubuntu.py`），文件名代表不同系统——
  云端因此知道他在哪台系统上，下发的命令可以针对该系统，不会

  Terminal 窗口就开始记录，对应一个 `日期-系统名.json`；记录的

  天然不入账，与 15:40 红线一致。）
- **退出命令**：输入一个特殊命令（例如 `macos(exit)`），客户端
